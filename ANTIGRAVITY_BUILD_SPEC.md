# Build Specification: Camera-Based Path Following + Live Dashboard

**Project:** Raspberry Pi Autonomous Vehicle — software prototype for Review-I  
**Primary goal:** Build a working laptop-based computer-vision prototype that detects a coloured path in images/video, calculates the path's position, produces simulated steering/motor-command proposals, and displays the full pipeline in a dashboard.  
**Primary user:** A student developing the software on Windows with an ordinary laptop. No Raspberry Pi, Arduino, motor driver, or physical car is assumed to be available.  
**Coding agent:** Google Antigravity (Claude Code can also follow the same specification).

---

## 0. Instructions to the coding agent

Read this entire file before editing code. Then implement the project in small, testable phases. Do not merely return a plan, create placeholder files, or claim the project is complete without running the application and tests.

### Non-negotiable rules

1. **Do not fabricate results.** FPS, latency, detection success, test counts, screenshots, and benchmark values must be generated by code that actually ran. Label results as synthetic, recorded-video, or laptop-measured as appropriate.
2. **No hardware claims.** All motor outputs are simulated proposals. Do not import GPIO libraries or send commands to hardware. Raspberry Pi deployment is a future step.
3. **No training in the initial MVP.** The baseline path detector uses OpenCV; it does not require a trained model. Do not download YOLO weights or start model training as part of the MVP.
4. **No paid/cloud dependency.** The core application must run locally on a normal Windows laptop. Do not require a paid API, a cloud account, or a GPU.
5. **Keep the scope narrow.** Do not introduce React, FastAPI, ROS 2, MuJoCo, depth estimation, object detection, MPC, or other subsystems into the MVP. They are outside this specification.
6. **Use recent, stable, compatible dependencies.** Before installation, check the current stable releases and official package documentation. Avoid prereleases. Choose versions that support the selected Python version and Windows. Record the exact versions that actually install and pass tests in `docs/VERSIONS.md`. Do not select an incompatible package solely because its version number is newer.
7. **Fail gracefully.** Missing webcam, unreadable video, absent path, bad configuration, or camera disconnect must produce a visible message and safe software state, not an unhandled crash.
8. **Verify rendered output.** Save representative overlay and mask frames, inspect them visually if the available tools allow it, and fix obvious errors before claiming the visual pipeline works.
9. **Keep modules separate.** Perception, controller logic, input sources, telemetry, and UI must be separate. Core logic must be testable without Streamlit or a camera.
10. **Explain the work.** Maintain `README.md`, `docs/EXPLAINER.md`, `docs/PROGRESS.md`, and `docs/KNOWN_ISSUES.md`. Explain important decisions in plain language so the student can answer viva/review questions.
11. **Use phase gates.** At the end of every phase, run its acceptance tests, update progress notes, and commit the phase if Git is available. Do not proceed while a core acceptance test is failing; investigate and fix it first. If blocked after reasonable attempts, document the issue and use a simpler fallback.
12. **Protect the user's files.** Do not delete or overwrite unrelated files. Put project outputs only in this repository. Keep raw user videos, temporary files, virtual environments, logs, and large generated files out of Git.

## 1. What we are building

A **software-in-the-loop demonstration** of the following pipeline:

`Image / video / webcam → OpenCV path perception → path error → steering decision → simulated left/right motor commands → dashboard + CSV log`

The first version is deliberately a classic-computer-vision baseline. It is useful for a high-contrast coloured line/tape and provides an interpretable point of comparison for any future learned model.

### MVP features

- Synthetic test mode that works even when there is no camera or video file.
- Recorded-video input, including videos recorded on a Samsung Galaxy S22 and copied to the laptop.
- Optional laptop webcam input.
- HSV-based colour segmentation with configurable thresholds.
- Noise filtering and a region of interest.
- Path centre/centroid estimation, a normalized lateral error, and a clear `PATH_LOST` status.
- A basic proportional or PD steering controller.
- Simulated outputs: `LEFT`, `STRAIGHT`, `RIGHT`, `STOP`, and bounded left/right PWM proposals (0–255).
- Streamlit dashboard with original frame, mask, annotated frame, status, steering, PWM proposals, measured FPS/latency, and error history.
- CSV event/telemetry logging.
- Automated tests for perception geometry, controller behavior, path-loss safety, output bounds, and synthetic examples.
- A short, reproducible demo script and screenshots saved from an actual application run.

### Explicitly out of scope for the MVP

- Physical vehicle movement, Raspberry Pi GPIO, Arduino firmware, or motor-driver integration.
- Neural-network training, YOLO, depth estimation, traffic-sign recognition, obstacle-distance estimation, MPC, GP policies, ROS 2, or a physics simulator.
- Claims that a laptop experiment proves real-world vehicle safety or Raspberry Pi performance.

These may be considered later, but they must not delay the MVP.

## 4. Functional details

### 4.1 Input modes

The dashboard must offer three selectable modes:

**A. Synthetic demo (must always work)**

- Programmatically generate frames with a yellow or other configurable high-contrast path.
- Include straight, curved, left-offset, right-offset, noisy, and missing-path cases.
- Use a deterministic seed where randomness is involved.
- Provide a simple way to switch between cases or play a short synthetic clip.
- Generate a corresponding ground-truth path centre for tests only. The perception and controller must not use this ground truth as an input.

**B. Video file (required for future Samsung Galaxy S22 testing)**

- Accept common file types such as MP4, MOV, AVI, and M4V where the installed OpenCV/video codecs support them.
- The UI must let the user upload/select a local video; do not hardcode one filename.
- Support play/start, pause where practical, reset/replay, and a clear message if the codec/file is unsupported.
- Also allow a local file path in configuration/CLI for reproducible tests.
- Process frames sequentially and show the processed frame, mask, and controller decision.
- Never assume the phone recording is labelled or use its frames for training automatically.

**C. Laptop webcam (optional but desired in MVP)**

- Use OpenCV `VideoCapture`.
- Check that the device opened successfully, report camera access errors, and release the capture handle cleanly when stopped or when the source changes.
- Provide a source fallback to synthetic mode or video-file mode if no webcam is available.

Do not require the phone to act as a live IP camera. A file recorded on the S22 and copied/uploaded to the laptop is sufficient for the first real-world test.

### 4.2 Path perception

Implement and document this baseline:

1. Read a BGR frame.
2. Convert it to HSV.
3. Apply configurable lower/upper HSV thresholds with `cv2.inRange`.
4. Apply a small morphological opening/closing operation to reduce speckles and fill small holes. Kernel size must be configurable or safely fixed to a small default.
5. Apply a region of interest (ROI), initially focused on the lower portion of the frame. Make ROI position/height adjustable if feasible.
6. Find valid connected contours/components and reject tiny blobs using a minimum-area threshold.
7. Estimate the path centre from appropriate pixels/contours in the ROI. For a simple initial method, use the largest qualifying path component's centroid. If it is more robust, compute centres at multiple horizontal bands and use a look-ahead point; document the method used.
8. Calculate normalized lateral error:

   `error = (path_center_x - image_center_x) / (image_width / 2)`

   The error should be approximately in `[-1, +1]`. Negative means the detected path is left of image centre; positive means it is right.
9. Set `path_valid = false` when there are too few valid pixels or no qualifying component. Never return a fake centre when the path is missing.
10. Return a structured result containing at least: valid flag, path centre, normalized error, mask, annotated frame, processing notes/area or confidence proxy.

The confidence proxy must be honestly described (e.g. detected pixel area or mask occupancy), not represented as a calibrated model confidence.

Default to yellow tape, but make thresholds configurable. Do not assume a single set of HSV values will work perfectly under every lighting condition; include calibration controls in the dashboard.

### 4.3 Steering controller

Implement a pure Python P or PD controller that receives perception output and elapsed time/delta error. It must not depend on Streamlit or camera APIs.

- Controller inputs: `path_valid`, normalized error, previous error, `dt`, base speed, controller gains, and a steering deadband.
- On valid path: compute a bounded turn command. Use documented sign conventions so a path to the left produces a left-turn proposal, and a path to the right produces a right-turn proposal.
- State labels: `PATH_LOST`, `LEFT`, `STRAIGHT`, `RIGHT`, and `STOP` (additional labels are okay if explained).
- On missing path: immediately request `STOP`, and output zero simulated motor commands. Do not keep steering blindly when path detection fails.
- Convert steering to differential left/right PWM proposals using a documented convention, and clamp each output to `[0, 255]` for the forward-driving demo. If reverse is later supported, represent direction separately rather than silently making PWM negative.
- Keep control gains, base speed, deadband, and limits in configuration.
- Test sign direction, saturation, zero-error behavior, large errors, invalid path, and controller stability for `dt <= 0`/invalid timing.
- All motor commands are **simulation-only proposals**.

### 4.4 Pipeline and metrics

The end-to-end pipeline should process a frame and return a structured output such as:

- frame timestamp/source name;
- original frame, mask, annotated frame;
- path-valid flag, path centre, normalized error;
- controller state and reason;
- left/right PWM proposals;
- measured processing milliseconds and calculated FPS.

Measure elapsed processing time with a monotonic high-resolution timer around actual work. Use measured results only; do not insert claimed performance figures or hardcode FPS.

### 4.5 Dashboard

Create a clean local dashboard with:

- A clear title and `SIMULATION / LAPTOP PROTOTYPE — NO HARDWARE CONTROL` notice.
- Input selector: Synthetic / Video File / Webcam.
- Video upload or file selection for recorded clips.
- Start/stop and reset controls appropriate to the selected source.
- HSV lower/upper bound controls and minimum component area.
- A view of the original frame and annotated output; also show the mask.
- Current state, path-valid indicator, normalized path error, path centre, proposed left/right PWM, measured processing time, and FPS.
- A rolling chart/history of path error and state changes.
- A CSV logging control and a clear path to the produced log file.
- Errors and warnings in the UI, not only in terminal output.
- A clear, visible status if the path is lost or the source cannot be read.

Do not sacrifice application reliability for decorative UI features. The vision/control pipeline must remain modular and testable without the dashboard.

Streamlit has rerun and session-state semantics. Implement frame handling carefully so the app doesn't reopen the camera on every rerun, leak capture handles, freeze indefinitely, or accumulate an unbounded number of frames in memory. Keep only the history needed for the live chart. Release resources when the input changes or the app stops, to the extent possible in Streamlit's execution model.

### 4.6 CSV telemetry

Each processed frame or controlled sample should be logged with a timestamp and fields such as:

`timestamp,source,frame_index,path_valid,path_center_x,normalized_error,state,left_pwm,right_pwm,processing_ms,fps`

- Use a unique log filename per run.
- Create the output directory automatically.
- Log invalid/missing path explicitly.
- Do not log the full image into CSV.
- Do not invent or backfill values for frames that were not processed.

## 5. Samsung Galaxy S22 recorded-video test (future user workflow)

Design the application so the user can later perform this test without modifying code or retraining anything.

### User workflow

1. Use the Samsung Galaxy S22 to record a coloured line/tape on paper or the floor from several angles and under different lighting.
2. Copy the clip to the laptop, or use the dashboard's video upload control.
3. Select **Video File** as the source.
4. Adjust HSV sliders and ROI/minimum-area settings until the mask isolates the path reasonably well.
5. Play the clip and observe the path mask, estimated centre, normalized error, controller state, and proposed PWM.
6. Save settings as a named calibration file, e.g. `configs/s22_yellow_tape.yaml`, and save a CSV log for that test.
7. Repeat with different clips and compare results. Do not tune on a clip and then report the same clip as an independent test.

### Suggested recording protocol for a meaningful test

- Use a clearly coloured tape on a contrasting floor or large sheet of paper.
- Record separate short clips: straight line, gentle curve, sharper bend, line near the left/right of frame, partial occlusion/gap, bright light, shadow, and dimmer indoor light.
- Keep enough of the track visible in the lower part of the image. Try both a stable oblique view and the approximate viewpoint you expect from a car-mounted camera.
- Avoid excessive motion blur. A stable 1080p recording is a reasonable starting point; lower resolutions can be tested later for speed.
- Do not assume the camera's auto-exposure/white balance will leave colour values unchanged between clips. Use the sliders to calibrate and save settings per tested environment if needed.

### Honest interpretation

This test validates path detection on recorded phone-camera footage. It does **not** validate physical autonomous driving, collision avoidance, Raspberry Pi speed, distance estimation, or closed-loop motor control.

No neural-network training or Colab notebook is required for this workflow.

## 6. Testing requirements

Create pytest tests before relying on the dashboard. At minimum:

### Synthetic image tests

- A centered path yields a centre close to image centre and near-zero error.
- A path on the left yields negative normalized error.
- A path on the right yields positive normalized error.
- A curve produces a valid path estimate or a documented invalid result; it must not crash.
- No path produces `path_valid=False` and a safe stop.
- Tiny isolated noise blobs are rejected below the configured minimum area.
- Changes in image dimensions do not break geometry.

### Controller tests

- Error sign produces the correct left/right steering direction.
- Near-zero error yields straight/low correction.
- Every PWM proposal stays within `[0,255]`.
- Invalid path yields zero commands and `PATH_LOST`/`STOP`.
- Invalid/nonpositive `dt` cannot produce NaN/inf or crash.
- Repeated stable samples do not produce uncontrolled output jumps; if a rate limit is implemented, test it.

### Pipeline/source tests

- Synthetic pipeline processes a frame end-to-end.
- Video-file source handles end-of-file and reset cleanly.
- Missing/unreadable file gives a human-readable error.
- Webcam-not-present fallback works.
- CSV log contains the expected fields and the actual run's number of records.
- The app does not need a GPU or network access to run in synthetic mode.

Use deterministic synthetic inputs in unit tests. Keep integration tests for real webcam/video optional so CI or a laptop without a camera doesn't fail.

## 9. Future optional ML experiment — not part of the initial MVP

Only consider this after all core phases pass and the user asks for the AI extension.

- Optional experiment: compare the OpenCV HSV baseline with a recent lightweight segmentation model fine-tuned to detect the coloured path.
- If any model training is undertaken, it must run **only on Google Colab Free tier**. Do not train on the laptop GPU/CPU, do not require paid Colab, and do not make the core application depend on training.
- Use the user's own recorded clips and/or synthetic frames with correctly generated/annotated path masks. YouTube videos are not required. A video is not a labelled dataset unless suitable frame-level masks/labels exist and its reuse licence permits the intended use.
- Keep training, validation and test clips separate by recording session; do not split near-duplicate frames randomly across all splits.
- Create one separate notebook, such as `notebooks/colab_train_path_segmentation.ipynb`, only when this extension is explicitly started. Include dependency/version cells, dataset upload/validation, training, validation plots, inference examples, export/download of weights, and a clean fallback if a free GPU/runtime is unavailable.
- Do not claim improved performance unless both approaches are compared on the same held-out images with the same metrics and measured latency.
- The baseline app must continue to run if the trained model/weights/notebook are absent.
